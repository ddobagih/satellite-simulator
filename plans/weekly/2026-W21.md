## 순차 의존 항목
1. Batch 1 정적 조사 결과를 먼저 모은다.
2. Windows 빌드, PPT/PDF, MP4/MOV, optional asset/SFX, Git LFS 여부는 사용자 또는 제출 기준 확인 전까지 완료로 쓰지 않는다.
3. Unity Editor를 여는 작업은 Batch 2에서 한 명이 순차 실행한다.
4. 자동 검증 또는 GUI 리허설이 실패한 경우에만 Batch 3 최소 수정 작업을 시작한다.
5. 코드/에셋 수정이 발생하면 자동 검증, GUI 리허설, 관련 빌드를 마지막 상태 기준으로 다시 실행한다.
6. 검증/빌드 결과가 확정된 뒤에만 README, WORK_LOG, Q&A, 제출 인벤토리를 갱신한다.
7. 제출 형식이 확정된 뒤에만 `Prepare Submission Folder` 또는 수동 `Submission/OrbitShare` 구성을 진행한다.
8. 마지막에 해당 날짜 daylog, Git 상태, 제출 산출물 목록을 확인한다.

## 리스크와 확인 필요
- 확인 필요: Unity `LicensingClient` IPC가 동작하는 환경을 사용할 수 있는지.
- 확인 필요: 실제 GUI/DISPLAY 환경에서 Play Mode와 Linux runtime smoke를 수행할 수 있는지.
- 확인 필요: Windows 실행 파일이 제출 필수인지, Linux 빌드만으로 충분한지.
- 확인 필요: `orbitshare-demo.gif`가 시연 영상으로 인정되는지, 별도 MP4/MOV가 필요한지.
- 확인 필요: 발표 PPT/PDF가 필수인지, 외부에서 따로 준비된 파일이 있는지.
- 확인 필요: `SatelliteModel.prefab`, `PremiumEarthMaterial.mat`, SFX 5종이 과제 필수인지 optional fallback 유지로 충분한지.
- 확인 필요: 50MB 초과 에셋을 Git LFS로 옮길지, private repo 유지 또는 제출 제외로 처리할지.
- 리스크: 현재 확실한 PASS 근거는 r1 보강 전 기존 `orbitshare-validation.md`이며, 최신 검증 코드 기준 PASS로 단정하면 안 된다.
- 리스크: headless `NullGfxDevice` 실행의 FMOD/shader 오류는 GUI smoke PASS 근거로 사용할 수 없다.
- 리스크: Unity 자동 검증, GUI 리허설, Resource Hook 검증, frame capture, 빌드를 병렬 실행하면 project lock/log 충돌이 날 수 있다.
- 리스크: 제출 형식 확정 전 `Submission/OrbitShare`를 만들면 포함 범위가 흔들릴 수 있다.
- 리스크: Asset Store 에셋과 대용량 리소스가 포함되어 있어 저장소 공개 범위와 제출 파일 범위를 잘못 잡으면 라이선스/용량 문제가 생길 수 있다.
- 리스크: `orbitshare_shared_satellite_agent.md` 아래쪽 legacy 관측 플랫폼 원문이 발표 기준과 충돌할 수 있으므로 상단 최신 섹션 기준으로만 발표해야 한다.

- PPT/PDF, MP4/MOV, GIF/PNG, `Submission/`의 제출 상태가 `존재/없음/확인 필요/제외 사유`로 분리된다.
- README, WORK_LOG, ASSET_STORE_IMPORT, asset-store-import-report, 발표 Q&A가 서로 충돌하지 않는다.
- 매일 daylog에 변경 파일, 실제 실행한 검증, 실패/미실행 검증, 남은 확인 필요가 기록된다.
